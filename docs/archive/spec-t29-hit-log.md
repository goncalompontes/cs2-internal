## 1. What exists today (the facts, with the code)

### 1.1 The event capture

`payload/control/src/events.cpp` patches the client's `CGameEventManager`
dispatch vtable slots (`FireEvent` `+0x38`, `FireEventClientSide` `+0x40`) and
records the fired events' **names and arguments** into a 64-entry ring
(`payload/control/include/cs2/control/event_ring.hpp:51`). The capture runs on
the **game thread** (`events.cpp:107-126`); the read side (the control channel
and the ESP's providers) runs on the control/render thread.

The default subscription set (`events.cpp:97-103`) is:

```
round_start, round_end, round_freeze_end, round_officially_ended, round_mvp,
begin_new_match, announce_phase_end, player_death, player_hurt, player_spawned,
other_death, bomb_planted, bomb_defused, bomb_exploded, bomb_dropped,
bomb_pickup, item_purchase, gameinstructor_draw, cs_win_panel_round,
client_disconnect
```

**`player_hurt` and `player_death` are in it.** The hit log therefore needs **no
new subscription** and **no new hook**.

> **Correction to `docs/feature-wave.md:316`.** The note says the payload
> "already captures `player_hurt`, `player_death` **and `weapon_fire`** with
> their arguments". The first two are true; **`weapon_fire` is not captured** â€”
> it is not in the default set (`events.cpp:97-103`) and nothing subscribes it.
> It *is* a known event (`event_names.hpp:284`), so it could be subscribed on
> demand â€” but it fires on **every shot**, and the ring it would share holds
> only 64 entries. This task does **not** subscribe it (Â§4).

### 1.2 What the captured arguments actually are â€” the six-field cap

This is the fact the feature-wave note glosses over, and it decides the shape
of the task.

`EventEntry::k_max_args` is **6** (`event_ring.hpp:30`), and `read_args` stops
at the sixth declared field (`events.cpp:271`). The build's own field lists
(`event_names.hpp`, generated by `scripts/extract-gameevents.py`) are, in
order:

| event | fields (the build's order) | the first six (what is captured today) |
|---|---|---|
| `player_hurt` | userid, attacker, health, armor, weapon, **dmg_health**, **dmg_armor**, **hitgroup** (`event_names.hpp:764-771`) | userid, attacker, health, armor, weapon, dmg_health |
| `player_death` | userid, attacker, assister, assistedflash, weapon, weapon_itemid, â€¦ `distance` (18th), `dmg_health` (19th), `hitgroup` (21st) (`event_names.hpp:727-748`) | userid, attacker, assister, assistedflash, weapon, weapon_itemid |
| `weapon_fire` | userid, weapon, silenced (`event_names.hpp:956-958`) | all three |

â‡’ **With the cap at 6 the hitgroup is not captured at all** (it is the eighth
field of `player_hurt`), and `player_death`'s own `distance` and `hitgroup`
(its eighteenth and twenty-first fields) are not either. The feature-wave's
"killfeed with the hitbox hit, the damage and the distance" needs the
hitgroup, so **the cap has to move**: this task raises
`EventEntry::k_max_args` from 6 to **8**, which captures every field of
`player_hurt` and leaves `player_death`'s tail uncaptured (its `distance` and
`hitgroup` are past eight).

The consequences of the raise, which the implementer must state in the report:

* the ring's footprint grows from 64 Ã— 536 B â‰ˆ **34 KB** to 64 Ã— 696 B â‰ˆ
  **45 KB** (it is static data inside the manually mapped image â€” `EventLog` is
  a member of `Service`, which is a member of the payload's namespace-scope
  `Runtime` global, `payload/src/payload_main.cpp:100`);
* `read_args` performs **up to eight** engine getter calls per captured event
  instead of six (each field is one vtable call into the engine,
  `events.cpp:286-306`). The default event set is low-rate, so this is
  negligible â€” but the `player_hurt` rate in a firefight is not;
* `docs/control-harness.md:444-445` says "`args` holds at most 6 fields per
  event" and must be updated to 8.

`player_death`'s `distance` therefore stays uncaptured. **The distance the log
shows is computed, not read** (Â§2.2) â€” which is also the only distance that is
available for a *hit* (a `player_hurt` carries no distance at all).

### 1.3 The slot trap

The event's `userid` / `attacker` / `assister` are the game's **player slots**
(0..63), not entity pointers. The snapshot keys its players by the
controller's **entity index** (`payload/game/include/cs2/game/snapshot.hpp:16`),
and the payload has no slot â†’ entity table. The repository already hit this
trap with the sound ESP: `docs/handoff-wave2.md:443-449` records that the
current code resolves the slot by its **rank** in the snapshot's player list
("the current code uses the *rank* in the snapshot's table, which is only right
while every lower slot is still connected").

The existing resolution is `resolve_sound_player`
(`payload/control/include/cs2/control/service.hpp:132-146`): the **rank** first
(the client creates the controllers in the server's slot order), the **exact
entity-index match** as the fallback, and `nullptr` when neither works. The
hit log uses **the same function** â€” see Â§2.2 and Â§5 (the resolution is moved
into a dependency-free header so both paths share one implementation).

### 1.4 The provider pattern â€” the sound ESP

The repository has already solved "the control module has the data, the
features module has the screen":

* `payload/control/src/service.cpp:2408-2476` â€” `Service::recent_sounds`
  reduces the event ring into a small typed buffer while the ring's lock is
  held, resolves the slots against a fixed-size player table
  (`service.cpp:1799-1813`), and hands the result to the caller.
* `payload/features/include/cs2/features/esp_cache.hpp:64-101` â€” the features
  module's own spelling of the answer (`SoundEvent`) and the provider
  callback (`EspProviders::sounds`).
* `payload/src/payload_main.cpp:499-512, 622-627` â€” the adapter
  (`on_sounds`) and the registry (`set_esp_providers`), which exist because
  **the control module cannot depend on the features module and the features
  module cannot depend on the control module** (the cycle the registry exists
  to break â€” `esp_cache.hpp:103-120`).

**The hit log is this pattern, with the sound's shape replaced by a hit's.**

### 1.5 The renderer

The features module draws into a `render::DrawList`
(`payload/render/include/cs2/render/draw_list.hpp`): `rect`, `filled_rect`,
`line`, `text` (with `centered` and `outline`) and `filled_poly`. The ESP's
builders fill it (`payload/features/src/esp.cpp:50-81`), and the **same list**
reaches both renderers: the in-process one directly
(`payload/features/src/overlay.cpp:494-497`) and the Vulkan fallback through
the published model (`payload/features/src/model_publisher.cpp:126-183`).

â‡’ **A hit log drawn into the draw list needs no wire change to be visible in
both renderers.** The wire's `Model` carries the draw commands; only a
*setting* would need a wire field (Â§2.4).

Two limits to note for the layout: the draw list has **no text measurement**
and no right-alignment â€” `Text::centered` centres the text on `x`
(`imgui_backend.cpp:162-169`, and the layer's identical branch at
`overlay/src/renderer.cpp:482-489`). A killfeed's lines are therefore
**centred on a column**, not right-aligned; a right-aligned feed would need a
measure function the draw list does not have (out of scope, Â§4).

## 2. The design decisions

### 2.1 Where the hit log lives (question 1)

**The control module owns the log's model; the features module owns the
pixels.** Concretely:

| the log's part | the module that owns it | why |
|---|---|---|
| the capture (the `player_hurt` / `player_death` entries) | `payload/control` | the events are captured there (`events.cpp`), and the control module is the only module that can reach the ring |
| the log's buffer, its lifetime and its expiry | `payload/control` | one place decides what is "in the log" |
| the slot â†’ player resolution and the distance | `payload/control` | the slot â†’ entity-index table lives there (`service.cpp:1799-1813`) and the sound provider already resolves there |
| the drawing (the killfeed and the indicators) | `payload/features` | the features module is the live UI (`docs/orchestration/feature-brief.md` Â§2) and owns the draw list |
| the **wire** | **untouched** | the draw list already crosses it (`model_publisher.cpp:126-183`) |

**Why not the other way round.** The features module cannot reach the event
ring (it has no dependency on the control module â€” that is the cycle the
provider registry exists to break, `esp_cache.hpp:103-120`), and the control
module must not draw (it "never touches the render path",
`payload/control/include/cs2/control/service.hpp:7`). The seam is therefore
the same one the sound ESP already uses: a **provider callback** in
`EspProviders`, adapted in `payload_main.cpp`, where both modules are visible.

**What the renderer needs from the wire: nothing.** The honest answer to the
question is that the *renderer* needs **no slice of the wire at all** â€” the
draw list carries the text and the arcs, and the model publisher carries them
to the Vulkan layer. The only thing a wire field would buy is a **menu
switch**, and that is priced in Â§2.4.

**The alternative â€” "the control channel only, no drawing" â€” is not enough.**
The control channel's `events` command already exposes the raw events
(`service.cpp:412-488`); the operator can read `player_hurt` today. What the
operator asked for is a *feedback loop*: a hitbox, a damage number and a
distance **at the moment of the fight**, on the screen, without a Python client
in the loop. A control-channel-only hit log would be a text protocol, not a
feedback loop.

**One consequence the implementer must design around.** The event ring is
**shared** and it can be flooded: the sound provider subscribes
`player_footstep` / `player_sound` lazily when the sound ESP is switched on
(`service.cpp:2389-2406`) â€” "the footsteps are the game's highest-rate event".
A 64-entry ring full of footsteps evicts the hit entries within a second.
â‡’ **The hit log does not read the event ring.** It gets its **own** small
buffer in the control module, fed **at capture time** from
`EventLog::record_event` (`events.cpp:240-265`) â€” the moment the event fires,
before anything can evict it. The hit log's fidelity then does not depend on
whether the sound ESP is on.

### 2.2 What a "hit" is (question 2)

**One entry per `player_hurt`, one per `player_death`.** The entry is typed
(the ring's strings are parsed once, at capture time):

| field | source | meaning |
|---|---|---|
| `attacker_slot`, `victim_slot` | `player_hurt.attacker` / `userid` (or `player_death`'s) | the game's **player slots** |
| `attacker_index`, `victim_index` | resolved by the **provider** (the render thread), Â§1.3 and Â§3.2 | the snapshot's **entity indices**; `-1` when the slot names no known player |
| `hitgroup` | `player_hurt.hitgroup` (the eighth field) | the engine's group id; `-1` when the field was not captured |
| `damage` | `player_hurt.dmg_health` | the health damage |
| `armor_damage` | `player_hurt.dmg_armor` | the armour damage |
| `weapon` | `player_hurt.weapon` / `player_death.weapon` | the engine's weapon name, verbatim |
| `distance` | **computed** (Â§2.2.1) | attacker â†’ victim, in world units |
| `death` | the event's name | `true` for a `player_death` entry |
| `sequence`, `time_ms` | the capture | the dedup key and the age |

**The parser looks the fields up by name, never by position.** The order is a
property of the build's resource file (`scripts/extract-gameevents.py`), and a
game update may reorder it. The existing `read_sound_fields`
(`service.hpp:82-108`) scans the captured arguments by key â€” the hit log's
parser does the same. A field that is missing leaves the entry's field at its
"unknown" value (`-1`), never a wrong one.

#### 2.2.1 The distance

`player_hurt` carries no distance and `player_death`'s is past the eight-field
cap (Â§1.2), so **the distance is computed**: the distance between the
attacker's and the victim's positions, in world units, at the moment the log
draws the entry.

* The positions are the snapshot's (`PlayerSnapshot::origin`,
  `snapshot.hpp:47`), resolved through the same slot â†’ entity-index mapping.
* The unit is Source 2's world unit (an inch): the display converts with
  `esp_geometry::units_to_metres` (`esp_geometry.hpp:24, 43-45`,
  `k_units_per_metre = 39.3701`).
* **It is an approximation, and the operator must know it**: it is the
  distance at *draw* time (â‰¤ ~33 ms after the capture, `overlay.cpp:438`), not
  at the moment of the hit. Two players cannot cross more than a few units in
  that time, so the number is right to within a fraction of a metre â€” but it
  is not the server's number, and the log must not claim it is. The report and
  the operator's checklist say so.

#### 2.2.2 The order, the count and the expiry

* **Order:** newest first (the killfeed's newest entry at the top, the older
  ones below it â€” the convention every game uses).
* **Count:** at most **8** entries are drawn at once. The log's buffer holds
  more (the control module's ring: **64** entries) so that the entries
  survive a burst.
* **Expiry:** an entry lives for **5 seconds** and then leaves the log. The
  lifetime is owned by the **control module** (it filters the entries by age
  when the provider is called), so "what is in the log" is one decision in one
  place. The provider also hands over the entry's **fade alpha**, so the
  features module does not need the lifetime constant and the two modules
  cannot disagree about it.

#### 2.2.3 What the log shows, and what it does not

The log shows **two kinds of line**:

* a **hit line** â€” `attacker â†’ victim Â· <damage> dmg Â· <hitgroup> Â· <distance>m` â€”
  for every `player_hurt` **that involves the local player** (the local player
  was hit, or the local player did the hitting);
* a **kill line** â€” `attacker [weapon] victim` â€” for every `player_death`.

**Why the hit lines are filtered to the local player.** The log is a
*feedback loop for the operator's own fights*: in a 10 v 10 bot match the
whole map generates `player_hurt` at a rate that would bury the operator's own
hits under dozens of lines a second. The kill lines are **not** filtered â€” a
killfeed is a killfeed, and the kill rate is low.

The filter is applied by the **features module** (it knows the local player's
entity index, `snapshot.local->index`), and it is a **display** decision, not a
capture one: the control module captures everything and the features module
chooses what to show.

**When a slot cannot be resolved.** The entry is still shown. The name becomes
`?` (a single question mark), the numbers (the damage, the hitgroup, the
distance) are still shown, and the payload counts the entry as *unresolved*
(Â§3.5). A `player_hurt` whose `attacker` is missing entirely (a world
object â€” a fall, a grenade with no owner â€” or the `-1` the engine sends for
"no attacker") is shown with an unknown attacker.

### 2.3 The damage indicators (question 3)

**In this task**, because â€” and this was checked, not assumed â€” **the ESP
already has both inputs**:

| the indicator needs | the ESP has it | where |
|---|---|---|
| the local player's view yaw | `snapshot.local->eye_angles.yaw` | `snapshot.hpp:52`; filled from the pawn's `m_angEyeAngles` at `payload/game/src/state_reader.cpp:83` |
| the attacker's position | the snapshot's players, resolved by the entity index | `snapshot.hpp:47`; the same lookup the sound ESP does (`esp_sound.cpp:28-39`) |
| the bearing of one world offset relative to the yaw | `esp_geometry::screen_direction(dx, dy, yaw)` â€” **already written, already host-tested** | `esp_geometry.hpp:113-126` |

â‡’ **No new engine access, no new offset, no new RE.** The indicator is
**pure geometry** on data the frame already carries
(`esp_detail.hpp:91-107`: the snapshot, the view, the width, the height, the
config, `now_ms`).

**What the indicator is.** A short-lived arc at a fixed radius around the
screen centre, pointing at the bearing of the damage's source, drawn for the
entries in which **the local player is the victim** (the outgoing case â€” "my
shot hit" â€” is the kill/hit line's job, not the indicator's). It fades over
its own, shorter lifetime (**1.5 s** â€” the features module's own constant; the
control module's 5 s lifetime is the *log's*, the indicator is the *flash*).

**The honest caveat, which the spec and the report must both state.** The
indicator's direction is computed against the **current** view yaw and the
attacker's **current** position, because the events carry no position and no
angles. The error is the attacker's movement and the player's turning between
the hit and the draw (â‰¤ ~33 ms for a fresh entry, more for one that has been
on screen a second). It points at *where the attacker is now*, not at where
the shot came from. In the common case (the attacker is where the shot came
from, and the player has not turned) the two are the same; when the player
turns, the indicator turns with them, which is the convention the genre uses.

**The third-person caveat.** The yaw used is the **pawn's** eye angles
(`m_angEyeAngles`), which are the player's aim, not the camera's. In first
person they are the same. In third person the camera's yaw differs (the
engine damps the camera yaw toward the view yaw â€” `docs/re/angle-split.md`,
`payload/game/include/cs2/game/camera.hpp:84-88`), so the indicator's bearing
is then relative to the player's aim rather than to the camera. The task
does **not** chase the camera's angles: the published per-slot view state is
build-specific and guarded (`camera.hpp:203-211`, refused on an unverified
build), and a wrong camera origin is worse than an aim-relative bearing. Say
so in the report.

### 2.4 The switch and the settings (question 4)

**This task changes `wire::Settings` â€” no, it does not.** The answer is
**no**, and the reasons are:

1. **The wire is a shared, versioned, cross-binary contract.** A change is a
   `wire::k_version` bump (13 â†’ 14, `wire.hpp:36`) plus **both** binaries
   (the payload and the Vulkan layer) rebuilt. The failure mode is not
   degraded, it is **total**: `segment_is_compatible` (`wire.hpp:286-294`)
   makes a stale binary **refuse the segment** â€” "a stale binary must refuse a
   segment it does not understand rather than read a block whose layout â€” and
   whose checksum â€” it does not know". In the **Vulkan-layer mode** (the
   fallback, `payload_main.cpp:641-660`), an operator who updates the payload
   but not the layer loses the **whole layer-rendered overlay**, not just the
   switch. (The default in-process renderer, ADR-0023, does not use the
   segment at all â€” but the layer is still a shipped artefact and must be
   rebuilt and deployed with the payload.)
2. **The precedent exists.** The triggerbot's settings are explicitly *not* in
   the wire block: "the block is versioned and full, so they travel through
   the control channel and the environment" (`service.hpp:281-291`), wired
   from `CS2_PAYLOAD_TRIGGER` (`payload_main.cpp:245-289, 576-589`).
3. **The feature is read-only.** The hit log writes nothing to the game â€” it
   reads events the payload already captures and draws text. It has none of
   the reasons the animfix, the anti-aim or the ragebot have for being off by
   default.

**The switch, then:**

* the **control channel**: `{"cmd": "hitlog", "args": {"on": true}}` â†’ the
  hit log's own status block (Â§3.5). The command also *queries* (no `on`
  argument â†’ the current state), like the other feature commands.
* the **environment**: `CS2_PAYLOAD_HITLOG=0` starts the feature **off**;
  unset or `1` starts it **on**. The payload's env is the *default*, and the
  control command owns the feature afterwards â€” the same shape as
  `CS2_PAYLOAD_TRIGGER` (`payload_main.cpp:576-589`).
* **the default is ON.** The operator asked for this feature (item 5 of their
  list) and it is the feedback loop the ragebot work is missing; it is
  informational and cannot affect the game. *If the orchestrator prefers the
  repository's conservative default (every added element off), the change is
  one line â€” but then the scenario has to switch it on and off again, exactly
  as the animfix scenario does (`scripts/scenario/scenarios/animfix.py:85,108`).
  This is the orchestrator's call; the spec says both are one line apart.*

**What a wire field would cost, if the orchestrator decides otherwise.** The

## 3. What to build

### 3.1 The control module â€” the log's model

**New: `payload/control/include/cs2/control/hit_log.hpp`** (header-only,
dependency-free: `<atomic>`, `<cstddef>`, `<cstdint>`, `<cstring>`,
`<string_view>` â€” it includes `cs2/control/event_ring.hpp` for `EventEntry` and
`cs2/game/math.hpp` for `Vec3`, both dependency-free).

* `struct HitEntry` â€” the typed entry (Â§2.2). A plain value type: **no
  pointers**, so it may be copied freely across threads.
* `class HitLog` â€” a fixed-capacity ring (**64** entries) with a spinlock in
  the style of `EventRing` (`event_ring.cpp:18-26`):
  * `push(const HitEntry&)` â€” the capture side (the game thread);
  * `visit(visitor)` â€” the read side (the render thread), **the lock is held
    for the whole walk** and no other lock may be taken inside it (the rule
    `service.cpp:2414-2416` states for the sound path);
  * the counters: `captured`, `hits`, `kills`.

## The orchestrator's decisions (2026-10-21)

The design asked for four; here they are.

1. **The default: on.** The operator asked for the hit log as a feature and it
   is read-only; it gives the feedback loop the ragebot work lacks. The
   scenario switches it off and on the way the animfix scenario does.
2. **No menu switch in this task.** The wire is a shared, coordinated
   resource between two separately compiled binaries; a follow-up that owns
   the wire may add one, and the spec prices that cost exactly.
3. **The volume filter stays**: the hit lines are the ones the local player
   is involved in, and every kill is shown.
4. **The file moves are allowed, but the resolution must be implemented
   once.** If the implementer prefers a smaller diff, the slot → player
   resolution must still have a **single** implementation shared by the sound
   path and the hit log — a duplicated resolution will be a review finding.

Two things this task may **not** forget, from the review rounds that ran
today:

* the payload is **manually mapped** — no `thread_local` in a detour, no CRT
  static init, no exceptions (`docs/re/camera-split.md` records what a
  `thread_local` in a detour does to the game);
* every address goes through the dumper's signatures (ADR-0012), and the
  event's arguments are read **by name**, never by position.
