## 2. The settings name table (generated)

The control command has to address a setting by name. The flat field names live
in `wire.hpp` (`esp_box`, `movement_thirdperson_distance`, …) and the offsets
are layout-dependent — hand-writing 87 entries is exactly the kind of thing that
drifts.

**Write `scripts/gen-settings-table.py`** that parses `wire.hpp`'s
`struct Settings` and emits `overlay/include/cs2/overlay/settings_table.hpp`:

```cpp
#pragma once
// GENERATED by scripts/gen-settings-table.py - do not edit.
namespace cs2::overlay::wire {
enum class SettingType : std::uint8_t { flag, number, colour, text, count };
struct SettingInfo {
  std::string_view name;    // the flat field name, e.g. "esp_box"
  std::string_view section;  // the "--- group ---" heading it sits under
  SettingType type;
  std::size_t offset;        // byte offset into Settings
  std::size_t size;          // 1 (flag) | 4 (number) | 4 (colour) | N (text)
  std::size_t count;         // element count for colour/text, else 1
};
inline constexpr std::array<SettingInfo, N> SETTING_TABLE = { ... };
auto find_setting(std::string_view name) noexcept -> const SettingInfo*;
}  // namespace cs2::overlay::wire
```

Rules:

- The generator must **fail loudly** if it cannot parse the struct — a silently
  empty table is worse than no table. Exit non-zero with a clear message.
- The table must cover **every** field exactly once, in declaration order, with
  the right offset and size. The offsets are computed from the declared types
  under `#pragma pack(push,1)`: `uint8_t` → 1, `float`/`uint32_t` → 4,
  `uint8_t[N]` → colour (N == 4) or a byte array, `char[N]` → text.
- The section comes from the `// --- <group> ---` comment lines in the struct.
- **Wire it into the build** the way `payload/meson.build` wires
  `scripts/gen-sdk.py` (a `custom_target` with `build_always_stale`), so the
  table can never be stale. If the generated header is simpler to check in
  instead, say so in your report — but then add a **test** that regenerates it
  and compares, so it still cannot drift.

**A host test must assert** that the table has one entry per field, that the
names match the struct's field names exactly, and that the offsets are right
(re-read a couple of known fields' bytes out of a `Settings` and check them).

## 3. The `settings` command

```jsonc
// get one or more
{"cmd": "settings", "args": {"get": ["esp_box", "movement_thirdperson_distance"]}}
→ {"ok": true, "result": {"values": {"esp_box": 1, "movement_thirdperson_distance": 64.0}}}

// set one or more
{"cmd": "settings", "args": {"set": {"esp_box": 0, "esp_color_enemy": [255, 0, 0, 255]}}}
→ {"ok": true, "result": {"changed": ["esp_box", "esp_color_enemy"],
                          "values":   {"esp_box": 0, "esp_color_enemy": [255, 0, 0, 255]}}}

// get everything
{"cmd": "settings", "args": {}}
→ {"ok": true, "result": {"values": { ...every field... }}}
```

- The keys are the **flat wire field names** (`esp_box`), not the config
  file's `<section>.<field>` keys. Say so in the doc.
- A flag takes `0`/`1` (or `true`/`false`); a number takes a JSON number; a
  colour takes an **array of four** integers 0..255 (`[r, g, b, a]`); a text
  takes a string.
- **Unknown key → an error**, not a silent no-op:
  `{"ok": false, "error": "settings: unknown key \"esp_bxo\""}`. A typo must
  not look like a successful write.
- A **wrong value type** → an error naming the key and the expected type.
- `changed` lists only the keys whose value actually **changed** (a set to the
  value it already had is not a change).
- The command **reads and writes the live settings block**, which the **menu
  owns** — the control service does not have it. So:

  Add to `Service` a pair of **typed accessors** (put them in a new
  `payload/control/include/cs2/control/settings_access.hpp`):

  ```cpp
  // The live settings block. The overlay menu owns it (ADR-0021); the control
  // channel reads and writes it through these accessors, so a control-side
  // change and a menu-side change are the same block.
  using SettingsReader = void (*)(void* context, cs2::overlay::wire::Settings& out);
  using SettingsWriter = void (*)(void* context, const cs2::overlay::wire::Settings& in);
  void set_settings_access(SettingsReader reader, SettingsWriter writer, void* context) noexcept;
  ```

  `control` may include `cs2/overlay/wire.hpp` — it is a **shared POD contract**
  between the payload and the layer, not a layering violation. Add the include
  directory to `payload/control/meson.build`.

- **The writer must go through the block's owner**, so the menu's next frame
  does not overwrite the change. In the **in-process** mode the owner is the
  menu's `settings_`; in the **layer** mode it is the shared segment. Register
  the accessors in `payload/src/payload_main.cpp` accordingly — **the menu and
  the publisher already know how to read and write their own block**; reuse
  that, do not invent a third copy.
- The payload's own features read the block through
  `features::from_wire_settings`, which **clamps** every numeric field. So an
  out-of-range value written here is clamped before it reaches a feature. Say
  that in the doc, and make the command's own error message reflect it (a
  number out of the field's range is *accepted and clamped*, not an error —
  unless the type is wrong).

## 4. The `batch` command (the "run a script" primitive)

```jsonc
{"cmd": "batch", "args": {"steps": [
   {"cmd": "exec", "args": {"line": "sv_cheats 1"}},
   {"cmd": "look",  "args": {"yaw": 90, "pitch": 0}},
   {"cmd": "press", "args": {"buttons": ["forward"]}}
]}}
→ {"ok": true, "result": {"results": [
      {"cmd": "exec",  "ok": true,  "result": {"queued": true}},
      {"cmd": "look",  "ok": true,  "result": { ... }},
      {"cmd": "press", "ok": false, "error": "unknown button \"foward\""}
   ]}}
```

- The steps run **in order, on the control thread**, exactly as if they had
  been sent one at a time. Reuse `Service::handle` for the dispatch — do not
  re-implement it — so a step's behaviour is identical to a direct request.
- **A failing step does not abort the batch**: it is recorded and the batch
  continues. The batch's own `ok` is `true` unless the *batch* itself was
  malformed.
- **Guard against recursion**: a step must not be a `batch`. Reject it with a
  clear error.
- **Bound the work**: a maximum step count (e.g. 64) and a maximum nesting
  depth of 1. Exceeding either is an error, not a truncation.
- The per-step results are the **same objects** the individual commands return.

## 5. The protocol version

The channel is **not versioned** today, which is why a stale client and a new
payload can disagree silently.

- Add a `protocol` field to the `ping` result: the **command-surface version**,
  an integer. Start it at **2** (the docs already call the current surface
  "v1"; the new commands make it v2).
- Add a `protocol` field to the **response envelope**? No — keep the envelope
  as it is (`{"id", "ok", "result"|"error"}`) so old clients still parse it.
  The version rides on `ping`.
- The **Python client** (a separate task) will check it. Document the number in
  `docs/control-harness.md` and in the `ping` row of the command table.

## 6. Also in scope (cheap, high value)

- **`events` — a `since` cursor.** Today a client that wants "what happened
  since I last looked" has to diff the `seq` numbers by hand. Add an optional
  `since` argument: a `seq`; the result contains only the events with
  `seq > since`, and the result gains a `last_seq` (the highest `seq` the ring
  holds) so the client can use it as its next cursor.
- **`log` — the payload's own log tail.** `cs2::game::append_log` already
  writes `%LOCALAPPDATA%\cs2-internal\cs2-payload.log`. Add a command that
  returns the last *N* lines (default 50, cap 500) so an agent can read what
  the payload said. **Read the file** — do not add a second in-memory buffer.
- **Fix the documented-but-ignored `heatmap` `target` argument.** The doc
  (`control-harness.md:105`) says `target` centres the chart on an entity
  index, the Python client sends it, and `do_heatmap` **never reads it** — it
  is silently dropped. Either implement it (centre the chart on that entity's
  eye) or remove it from the doc *and* the Python client. **Implementing it is
  better** — the aim machinery already has the per-target data. If you
  implement it, say how the chart's basis changes.

  fully-qualified `std::`, **no exceptions**, no new global mutable state
